# 从局部拼接到可跑图空间：奶蛙 WFC 白盒关卡实践综述

日期：2026-10-18　｜　Unity 6000.6.2f1 / URP　｜　项目：Milkfrog

## 1. 实践问题与完成目标

这次实践尝试回答一个具体问题：能否通过波函数坍塌算法，快速生成一张让现有奶蛙角色实际行走、跳跃和战斗的三维白盒关卡？交付物是一张独立实验场景、Windows 试玩包和可复现的验证数据。关卡采用单层房间与走廊，不设置屋顶，用少量颜色区分起点、出口及遭遇房间，主要观察空间连接和角色尺度。

“看起来像地图”和“能够跑图”是两种要求。前者可以由模块邻接规则描述，后者还涉及整图连通、门洞净宽、墙体碰撞、角色出生净空及敌人行为。因而，本项目采用主通路约束、WFC 模块求解和全局验收组成的混合流程。主通路、至少四个房间和回接环路属于人为加入的设计要求，不能全部归因于普通 WFC 的局部规则。

这也界定了 Demo 的用途：它是可观察、可调参、可验证的空间生成实验，尚不是完整的随机地牢游戏。出口不要求清怪，两个遭遇点服务于战斗空间检查，不包含奖励、任务或主线存档。

## 2. WFC 如何变成可实现的规则

WFC 的名称借用了“观察”和“坍塌”的比喻，本实践实际执行的是离散约束求解。原作者仓库区分了从样本提取局部模式的 overlapping model 与直接定义模块邻接的 simple tiled model；这次使用后者，更方便把规则直接对应到三维门洞和墙体。[原作者项目说明](https://github.com/mxgmn/WaveFunctionCollapse)提供了算法和模型的原始背景；[Karth 与 Smith 的研究](https://escholarship.org/uc/item/1f29235t)则从约束求解角度讨论这一方法。

每个网格起初保存一组可能模块。若某格选定北向开口，其北侧邻格就必须选择南向开口的模块；不满足条件的候选被删除，删除又可能继续影响其他格。传播结束后，再从仍有多个候选的格子中选择加权熵最小的一格，根据模块权重抽取一个状态。这里“最小熵”表示优先解决选择最受限制的位置，而非按固定行列扫描。

本项目使用的加权 Shannon 熵为：

\[
H=\ln\left(\sum_i w_i\right)-\frac{\sum_i w_i\ln w_i}{\sum_i w_i}
\]

其中只统计该格当前仍合法的候选。单一候选的熵为零，空候选集合表示矛盾。权重影响被选中的倾向，不等于最终地图中模块数量的精确比例；邻接、边界和主通路都会改变输出分布。

求解器用 64 位位集保存最多 63 种状态，默认只有 31 种。四个方向的兼容集合预先计算，传播使用队列；每次决策保存候选快照及尚未尝试的替代状态。遇到矛盾后恢复快照并改选，达到回溯上限才重试。小规模地图使用完整快照容易理解和调试，但不是大地图的最省内存方案。

## 3. 从模块到空间：尺寸、接口与主通路

![模块规则与接口](Figures/modules.png)

默认网格为 10×10，每格边长 8 米。走廊净宽 3 米，墙高 3 米，地板厚 0.3 米。走廊原型包含尽端、直道、转角、丁字和十字，旋转去重后得到 15 种接口状态；房间复用这 15 种门口组合，另外增加一个空格，共 31 种状态。房间占满单格，走廊只占中央及开放方向的通道。

接口使用四位掩码：北、东、南、西分别为 1、2、4、8。相邻两边必须同时开放或同时关闭；地图外边界一律关闭。模块配置决定接口，几何生成器也读取同一份接口来放置地板、墙段和门洞。这避免了“逻辑上可以连接，实际却生成一堵墙”的双份规则问题。新增外观变体时，也必须维持这个对应关系。

主通路从网格西南内侧连接东北内侧，按种子随机决定向北或向东推进；另一条首段方向不同的路径提供回接。约束只要求相关接口存在，保留其余开口和模块类型的选择空间。起点、出口及主路约三分之一、三分之二处被要求使用房间模块，后两处作为遭遇点。

因此，WFC 仍然决定其余格子的模块、房间分布以及附加连接，但主线端点与基本环路已经受到强约束。这个选择提高了可玩性，也引入明显的方向偏置：本次默认地图的起终点最短距离都为 14 条格间连接，即 112 米中心线距离。不能把它描述成路线长度和节奏完全自由的生成器。

## 4. 全局连通与失败处理

仅匹配门口，并不能排除互不相连的小团块。本项目在普通邻接传播之后，增加“可能连通”检查：沿当前候选仍可能开放的接口，从起点搜索。如果某一区域已经不可能与起点连接，它只能变为空格；若其中存在不能再变空的模块，就判为矛盾并回溯。这属于额外的全局约束。

最终地图仍需独立验收，检查接口一致、边界封闭、全部可走格连通、起终点可达、至少四个房间及至少一个环路。环路统计使用图的独立环路数 E−V+C，其中 C 是连通分量数量；只有已连通的地图才能简化为 E−V+1。对照实验中的断开地图也必须使用完整公式，避免出现没有实际意义的负环路数。

每次求解最多回溯 2048 次，每个种子最多尝试 32 次。达到预算就显示失败原因，保留上一张有效地图；首次生成失败则停留在控制面板。求解阶段不创建关卡物体，只有通过验收后才建立候选场景、检查出生点并替换旧关卡。这使“失败”成为可解释的结果，而不会让角色突然站到一张半成品地图中。

## 5. Unity 接入：碰撞、角色与简单遭遇

为了避免主线固定边界、任务和存档位置校验干扰实验，PCG 使用独立会话，直接复用现有 Player Prefab、CombatActor、动画表现、输入和避障镜头。角色的移动速度、跳跃参数、垫步距离及战斗配置沿用项目资产；地图尺寸围绕这些条件设计。

白盒全部使用实际地板和墙体碰撞，出生前执行地面射线及胶囊净空检查。门洞的理论宽度只是第一步，还要让真实 CharacterController 通过转角和模块接缝。Unity 的[角色控制器说明](https://docs.unity3d.com/6000.0/Documentation/Manual/class-CharacterController.html)解释了沿墙滑动、台阶高度与坡度等行为；本 Demo 保持同一地板标高，先减少台阶与坡度带来的额外变量。

两个指定房间各放一名已有小怪，保留模型、攻击资产和 EnemyBrain。现有 AI 使用直线靠近，没有跨房间寻路，因此只在玩家同处一个开阔房间且有视线时交战。玩家离开后，小怪结束交战并返回出生点；房间边界限制它继续追入走廊。这是有意保留的能力边界，而不是让直线 AI 在随机迷宫中反复撞墙。

控制面板支持指定种子、重建及换图。F3 切换观察模式，角色暂停；在观察模式按 R 可以重新观看该种子的初始化、坍塌、传播、回溯和完成过程。格内数字显示候选数量，颜色区分走廊、房间和当前决策。暂停、切换及换图时清理输入和动作残留，避免界面点击变成游戏攻击。死亡或异常跌落后重置同一种子及全部遭遇，不写入主线磁盘存档。

## 6. 固定种子实验与结果

实验采用种子 0–99，比较正式混合方案和移除主通路、指定房间及可能连通检查后的 WFC 对照。两组使用相同模块、权重、地图尺寸和尝试上限。对照组在生成后自动选起点及该分量内的最远点，但同样接受整图连通、房间数量和环路检查。这是本实现内部的约束消融，不是对不同 WFC 库的性能排名。

| 指标 | 混合方案 | 取消主通路与全局连通约束 |
|---|---:|---:|
| 至少得到一个局部合法解的种子 | 100/100 | 100/100 |
| 通过全部整图验收的种子 | 100/100 | 0/100 |
| 每个种子平均累计求解耗时 | 3.20 ms | 59.39 ms |
| 每个种子最大累计求解耗时 | 8.35 ms | 82.29 ms |
| 平均回溯次数 | 5.86 | 0 |
| 最后一个局部解的平均可走格数 | 77.63 | 70.89 |
| 从选定起点平均可达格数 | 77.63 | 12.37 |

![批量生成结果](Figures/benchmark.png)

耗时来自本机 Unity Editor 中的求解计时，不包括等待观察播放、几何实例化、资源导入和渲染。对照组通常要消耗完整的 32 次尝试，因此其累计耗时更长，不能据此断言单次普通 WFC 比混合方案慢。

种子 18 的正式地图有 71 个可走格、14 个房间和 6 个独立环路，全部可走格连通。对照组第 32 次局部解有 72 个可走格，但从自动选定起点只能到达 5 格。这个失败样本直观说明：每个接头都合法，仍然可能得到许多互不相连的片段。

“0/100”只对本模块集、权重、预算和验收条件成立，不能推广成 WFC 无法生成可玩关卡。对照还同时移除了多项约束，无法单独量化主通路和连通检查各自的贡献；若继续研究，应加入“仅主通路”和“仅连通约束”两组实验，并扩大种子和模块范围。

原始统计位于[基准 CSV](../../Assets/CombatDemo/Validation/PCG/benchmark.csv)。[离线检查结果](../../Assets/CombatDemo/Validation/PCG/offline-checks.json)使用相同求解源码验证复现与预算，只替代 Unity 配置基类及属性声明，不能代替 Unity 物理与战斗验收。

## 7. 验证证据与可观察限制

最终回归：EditMode **166/166**、带图形设备的 PlayMode **183/183**，均无失败及跳过；Windows 构建成功。独立 Windows Player 隐藏启动后，种子 18 生成、角色位移、两个小怪及两台相机的 URP 离屏渲染检查通过，进程以 0 退出。离屏画面不包含 GUI；本文中的界面截图来自 Unity Editor。人工键鼠手感尚未作为验收证据。

验证分成算法、实际控制器、运行画面及独立构建四层。算法测试检查旋转去重、熵、传播、回溯、无解终止和种子复现；物理测试让真实角色走过门洞、转角及接缝，并尝试贴墙跑动、跳跃和垫步；玩法测试检查遭遇与返回、伤害、输入清理和换图重置。纯几何检查临时关闭敌人的角色碰撞，避免把正常的活体阻挡误判成门洞错误；战斗测试另行保留这些碰撞。

## 8. 复现方式与后续判断

在 Unity 打开 `Assets/CombatDemo/Scenes/PCG_Whitebox.unity` 后进入 Play，或运行完整试玩目录中的 `MilkfrogPCG.exe`。WASD 移动，鼠标转镜头，空格跳跃，Shift 垫步，左键攻击，右键防御，中键选敌；Esc 打开面板，R 重建，N 换下一个种子，F3 观察，F4 停止自动播放并单步。观察界面支持调整播放速度。种子复现以模块配置和求解器版本相同为前提，修改权重或约束后不能期待旧地图不变。

`Tools/Validate-Pcg.ps1` 可运行 Unity 基准、回归、截图和构建，支持按阶段执行；`Tools/Test-PcgOffline.ps1` 提供独立的算法检查入口。验证时需要关闭同一项目的交互编辑器，避免同时打开工程。源码新增部分集中在 PCG 模块，原有主线和黄牛试炼改动保留。

这次实践的主要收获是把“局部合法”和“整体可玩”拆成可独立检查的条件。WFC 适合表达模块接合关系，并在约束内提供变化；主通路、角色尺度和最终验收则把这种变化组织成可使用的空间。继续迭代时，应先降低固定西南—东北路线的偏置，加入更丰富的房间内部布局和空间节奏指标，再考虑多层接口、坡道、跨房间寻路与美术替换。增加维度之前，需要先确认生成多样性确实转化为了不同的跑图体验。
